# OpenKBP (as used by RADIANT) — usefulness for OpenBragg

> **Where this lives / why.** There is no existing research-notes convention in this repo. `docs/research/` is a sensible home for source-cited investigation notes that inform design but are not product/architecture spec (`PRD.md`) or domain glossary (`CONTEXT.md`). This file was chosen as that home. Every non-obvious claim is cited inline to a primary source; where a claim could only be verified from a search snippet or a paywalled record rather than a directly-fetched primary PDF, that is stated explicitly.
>
> Research date: 2026-07-10.

## Bottom-line verdict

**OpenKBP is a photon dataset and does not supply what OpenBragg's Phase-1 pipeline actually consumes or validates — it is *not* a drop-in fixture, and it cannot be used for the proton dose-recalculation / gamma-verification loop at all.** It contains 340 head-and-neck **IMRT (photon)** cases as **preprocessed CSV arrays on a fixed 128×128×128 grid** — CT + a clinically delivered **photon** dose distribution (Gy) + structure masks + a "possible dose" mask — and **no beam geometry, no fluence/MLC, no plan, and (obviously) no proton spots or RTION plan** ([Babier et al. 2021, arXiv HTML](https://ar5iv.labs.arxiv.org/html/2011.14076); [open-kbp README](https://github.com/ababier/open-kbp/blob/master/README.md)). Because OpenBragg's Dij→dose→gamma pipeline needs a **proton RTION plan (spots + weights) plus a proton reference RTDOSE** to have anything to recompute and compare against, OpenKBP supplies **none of the load-bearing inputs**. Its one salvageable asset is **anatomy** (CT in Hounsfield units + contoured OARs/PTVs), which *could* in principle be repurposed as geometry onto which a synthetic proton plan is invented and run through MCsquare — but two properties undercut even that: the CT is **spatially downsampled to a coarse ~3–4 mm 128³ grid** (proton range is acutely sensitive to CT resolution), and it is stored as an **offset/clipped 12-bit value range (0–4095), not raw true-HU DICOM**, which weakens the HU→relative-stopping-power path OpenBragg depends on. **Recommendation: skip OpenKBP for Phase 1; the real bottleneck (proton plan + spots + reference dose) is met far better by the proton example cases in matRad and especially OpenTPS.**

**Key implication for OpenBragg:** the dataset is *dose-prediction-shaped* (predict dose from CT+contours), not *dose-recalculation-shaped* (recompute dose from a plan and compare). ## RADIANT — what the paper is and how it uses OpenKBP

- **Full title:** *RADIANT: A fully configurable radiotherapy dose prediction framework.*
- **Authors:** Josiane Pafeng, Adrian Celaya, Skylar Gay, David Fuentes, Mary Martel, Laurence Court, Tucker Netherton (MD Anderson group). ([Crossref record, DOI 10.1088/2057-1976/ae7090](https://api.crossref.org/works/10.1088/2057-1976/ae7090))
- **Venue / year:** *Biomedical Physics & Engineering Express*, vol. 12, issue 3 (2026); medRxiv preprint `2025.06.20.25330029` (posted 2025). ([Crossref](https://api.crossref.org/works/10.1088/2057-1976/ae7090); [medRxiv](https://www.medrxiv.org/content/10.1101/2025.06.20.25330029); [IOPscience](https://iopscience.iop.org/article/10.1088/2057-1976/ae7090))
- **What it is:** a **deep-learning dose-prediction framework** — a configurable pipeline for data preprocessing, model configuration, training, and evaluation, built on the Medical Imaging Segmentation Toolkit (MIST), supporting multiple architectures (nnU-Net, FMG-Net, W-Net, ddU-Net, Swin UNETR) and optimizers. It is **not** a diffusion-specific paper and **not** a Monte Carlo dose engine. ([IOPscience abstract, search-surfaced](https://iopscience.iop.org/article/10.1088/2057-1976/ae7090); [medRxiv PDF, search-surfaced](https://www.medrxiv.org/content/10.1101/2025.06.20.25330029.full.pdf))
- **Modality — photon:** it targets **photon** plans for **cervix, prostate, and head-and-neck** sites. Cervix/prostate plans come from the Radiation Planning Assistant; the **head-and-neck** benchmark is the **AAPM OpenKBP challenge data**. No proton data is involved. ([search-surfaced abstract text](https://iopscience.iop.org/article/10.1088/2057-1976/ae7090))
- **How it consumes OpenKBP:** as a **held-out benchmark for the dose-prediction task** — models take the OpenKBP **CT + structure/contour masks** as input and **predict the 3D dose**, scored with the challenge's own **dose score** and **DVH score**. Reported OpenKBP head-and-neck results: **dose score 2.702, DVH score 1.495** (competitive with top challenge entries). ([search-surfaced results](https://iopscience.iop.org/article/10.1088/2057-1976/ae7090))

> **Verification caveat:** IOPscience and the medRxiv PDF both returned HTTP 403 to direct fetch. Title/authors/venue/DOI are confirmed from the **Crossref** primary metadata record. The narrative (photon; sites; MIST-based; architectures; dose score 2.702 / DVH score 1.495) is taken from search-engine snippets of the IOP/medRxiv/ResearchGate records rather than a directly-fetched PDF; treat the exact numeric scores as reported-but-not-independently-re-fetched.

**Why RADIANT matters here:** it confirms the *use pattern* OpenKBP is built for — a photon **dose-prediction ML benchmark**, i.e. learn CT+contours → dose. That is orthogonal to OpenBragg's Phase-1 mission (physics-based proton dose **recalculation** from a plan, verified by gamma). RADIANT using OpenKBP is not evidence that OpenKBP fits OpenBragg; it is evidence of the opposite use case.

## Fit vs OpenBragg Phase-1 needs

OpenBragg Phase 1 ingests a **DICOM-RT proton case** (CT, RTSTRUCT, RTION plan with spot weights, RTDOSE), builds a Dij, computes dose = Dij·w, and runs a **gamma (3%/3mm, 2%/2mm) + DVH** regression against a reference dose. Mapping each need:

| OpenBragg Phase-1 need | Does OpenKBP supply it? | Notes |
|---|---|---|
| **Proton DICOM-RT case** (CT/RTSTRUCT/RTION/RTDOSE) | **No** | Data is CSV arrays, not DICOM; and it is photon, not proton. No RTION/RTPLAN at all. |
| **True-HU CT** for HU→RSP conversion | **Partial / compromised** | CT is nominally in HU but stored as an **offset, clipped 12-bit range (0–4095)** and **spatially downsampled to 128³ (~3–4 mm)**. Not raw diagnostic true-HU DICOM. Coarse resolution + high-end clipping (bone/metal) degrade proton range/RSP fidelity. |
| **RTION plan + spot map + spot weights** (the `w` in Dij·w) | **No** | The dataset deliberately omits *all* plan/beam/fluence data — that omission defines the KBP prediction task. |
| **Proton reference dose (RTDOSE) for gamma** | **No** | The provided dose is a **photon IMRT** distribution; useless as a proton gamma/DVH oracle. |
| **Anatomy/geometry to synthesize a proton test case** | **Weakly yes** | CT (HU) + OAR/PTV contours could seed a *synthetic* proton case: invent a plan, run MCsquare, self-compare. But then OpenKBP is just anatomy — the coarse 128³ grid + offset/clipped HU undermine even this, and matRad/OpenTPS anatomy is at least as good with far less rework. |

**Net:** OpenKBP satisfies **0 of the 4 core Phase-1 inputs** (proton DICOM case, RTION plan+spots, proton reference dose) and only **partially** the CT-anatomy input, with resolution/HU caveats that specifically bite proton dose calculation.

## Alternatives / recommendation

The user's real bottleneck is **CT + a proton plan (spots/weights) + a reference proton dose** — a full proton DICOM-RT case. On that criterion:

- **OpenTPS (best fit).** Open-source Python proton TPS; imports/exports DICOM **CT, RTSTRUCT, RTDOSE, and RT ion plan (RTION)**, and ships example proton cases (e.g. a brain arc-proton case). Because it is a proton TPS, it can *produce* the exact quartet OpenBragg needs (proton plan with spots + a reference proton dose on real anatomy), and it is already OpenBragg's Phase-1 validation oracle. ([OpenTPS arXiv 2303.00365](https://arxiv.org/pdf/2303.00365); [opentps.org](https://opentps.org/))
- **matRad (good fit for geometry + in-house proton dose).** Ships **five** anonymized example datasets — box phantom, **prostate, liver, head-and-neck**, and the **TG119** IMRT phantom (CT+contours, from the CORT dataset) — plus generic **proton** machine base data, so it can generate a proton pencil-beam plan and reference dose in-house, and export DICOM. Good source of anatomy + a self-consistent proton plan/dose fixture. ([matRad CORT wiki](https://github.com/e0404/matRad/wiki/The-CORT-dataset); [Wieser et al. 2017, Med Phys](https://aapm.onlinelibrary.wiley.com/doi/10.1002/mp.12251))
- **Open proton DICOM datasets on TCIA, etc.** I could **not** verify, from primary sources, a well-known fully-open **proton RTION-plan + RTDOSE** collection on TCIA; the proton PBS DICOM-RT data surfaced in the literature is institutional/registry-based, not an open public collection. Flagging as unverified rather than asserting one exists. ([TCIA search context](https://www.cancerimagingarchive.net/))

**Recommendation:** Do **not** adopt OpenKBP for OpenBragg Phase 1. It is the wrong modality (photon), the wrong shape (dose-prediction, no plan), and the wrong CT fidelity (downsampled/offset, not true-HU DICOM) for a proton dose-**recalculation** + gamma pipeline. Stay with **matRad** and **OpenTPS** proton example cases as fixtures (OpenTPS especially, since it emits real proton DICOM-RT with an RTION plan and reference dose). Only revisit OpenKBP if a *photon* pathway or a pure anatomy library is ever needed — and even then prefer native-resolution DICOM CT.

## openkbp-opt — the optimization companion (does it fill the plan/Dij gap?)

> Research date: 2026-07-10. Everything below is from **directly-fetched primary sources**: the repo source code (`ababier/open-kbp-opt`, read via the GitHub API), its README, the **open-access PMC full text** of the paper (PMC10696540), and the **Crossref** metadata record. IOPscience was *not* directly fetched (it 403s), but every fact here is sourced from one of the directly-fetched artifacts above; where a value is genuinely absent from all accessible primary sources it is marked "not stated."

**Verdict — yes, this is the missing piece, for *photons*.** Where plain OpenKBP ships only CT + delivered dose + masks (no plan, no beam, no matrix), **openkbp-opt adds exactly the artifact OpenBragg's `Dij·w` model consumes: a precomputed, per-patient, sparse photon dose-influence matrix `Dij` (voxels × beamlets), plus reference and optimized plans.** Dose is `d_v = Σ_b D_{v,b} w_b`, and the repo's own optimizer computes it as `dose = patient.dij * w_opt` — the identical object and identical algebra as OpenBragg's Dij-first design ([optimizer.py](https://github.com/ababier/open-kbp-opt/blob/master/provided_code/optimizer.py); [paper, PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC10696540/)). It ships **100 patients** (the OpenKBP *test* set, same anatomy/grid), each with the `Dij`, a reference (clinical ground-truth) dose, 21 predicted doses (19 "high-quality"), CT, masks, feasible-dose mask, voxel dims ([README](https://github.com/ababier/open-kbp-opt/blob/master/README.md)); an optional 13 GB bundle adds the **fully optimized KBP plans** (fluence, beamlet weights, dose, gap) for all 7600 pipelines. So **OpenKBP + openkbp-opt together *do* form a self-contained open dataset for a photon `Dij·w` optimization / dose-recomputation pipeline** — you can load `Dij`, optimize or apply weights `w`, recompute dose, and score DVH/gamma against a reference. The two decisive caveats: (1) it is **photon IMRT, zero proton content** — no spots, no proton `Dij`; and (2) the `Dij` is **precomputed by CERR's IMRTP** and merely *consumed*, so it exercises OpenBragg's optimizer/recompute half but **bypasses the dose-engine seam** that is OpenBragg's primary seam (see nuance note below).

### Architectural nuance — which half of OpenBragg this exercises

OpenBragg's **primary seam is the dose engine**: `(image + material map + beam/geometry + plan spots) → Dij (+ geometry/units metadata)`. Everything downstream (`Dij·w` → DVH → gamma → Phase-2 inverse optimization) talks only to `Dij`. openkbp-opt hands you a **precomputed `Dij` (from CERR IMRTP)**. Consuming it therefore:

- **Exercises the downstream/optimizer half fully** — it is a genuine, ready-made photon `Dij` on real anatomy, so the `Dij·w` recompute path, DVH, gamma, and the Phase-2 dose-mimicking / inverse-optimization machinery all have a real fixture to run against (indeed openkbp-opt *is* a KBP dose-mimicking optimizer over this `Dij`, a close analogue of OpenBragg's Phase-2). This is exactly the object plain OpenKBP could not provide.
- **Bypasses the dose-engine seam** — you are *consuming* a `Dij`, not *producing* one from image+beam geometry, so this fixture does **not** exercise or validate OpenBragg's engine-wrapping seam (MCsquare/OpenTOPAS invocation, HU→material mapping, beam-model → `Dij`). It validates the "after the seam" contract, not the seam itself.
- **If you tried to *reproduce* the `Dij`** from the shipped CT (to test the seam), you would (a) need a photon beamlet engine (CERR/IMRTP or matRad-style pencil beam, not a proton engine), and (b) hit the **same 128³-downsampled, offset/clipped-HU CT-fidelity caveat** carried over from OpenKBP (§ CT/HU above) — less punishing for photons than protons, but still not diagnostic-resolution true-HU DICOM.

Net for OpenBragg: if the project pivots to **photon** first, openkbp-opt is a strong, self-contained fixture for the **`Dij`-consumer** side of the pipeline (recompute + DVH + gamma + inverse optimization) and a real-world analogue of the Phase-2 optimizer — but it is a photon dataset that supplies a *precomputed* `Dij`, so it does not test the engine seam, and it contributes nothing to the proton pathway.

## Correction (2026-07-22) — the beamlet weight vector `w` is `plan-fluence`, not `plan-weights`

While planning the photon-first pivot I read `provided_code/optimizer.py`, `resources.py`, and `general_functions.py` directly and found this note mislabels which artifact carries the beamlet intensity vector `w` (the `w` in `dose = Dij·w`). The facts-table rows above that gloss `plan-weights` as "(`w`)" are **wrong**. The verified mapping:

- **`plan-fluence/<pred>/<pt>.csv` IS `w`** — `save_fluence_and_dose` builds `w_opt = [w.SolutionValue() for w in self.w.values()]` (the continuous beamlet intensities), writes it to `get_fluence_path()` as a CSV with a `data` column, then writes `dose = patient.dij * w_opt` to `get_dose_path()`. So `plan-dose = Dij · (plan-fluence)` **by construction**.
- **`plan-weights/<pred>/<pt>.csv` is NOT `w`** — it is the per-*objective* table (`objective_df`), a DataFrame indexed by objective/constraint name with columns for the objective's dual weight and optimized/input objective values. `load_file` even special-cases it (`"/plan-weights/" in file_name`) and reads it with named columns `["Objective","Weight","Optimized objective","Input objective"]`. Irrelevant to dose recompute.

Consequence for a recompute pipeline: load `dij.npz` (base bundle) + `plan-fluence` and `plan-dose` (optional bundle) for one `(model, prediction-set, patient)`; `(dij @ w).reshape(128,128,128)` reproduces `plan-dose` to floating-point precision. Also note openkbp-opt's own scoring is dose-score (MAE over the feasible-dose mask) + DVH-score — **not** gamma. See `docs/superpowers/specs/2026-07-22-photon-first-pivot-design.md` for the full verified on-disk format table.
